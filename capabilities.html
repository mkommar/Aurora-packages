01 / Current system

Small surface. Real machinery.

Aurora is already more than a boot screen. Its current target is deliberately bounded: an original x86-64 kernel and userspace stack exercised through BIOS and QEMU.

Capability map

What is here now.

SHIPPED

Boot & core

Original x86-64 kernel with a BIOS-focused boot path and QEMU test loop. Paging, scheduling, process address spaces, fault containment, and a bounded native ABI form the execution core.

Test lens: QEMU guest regressions and host-side checks.
SHIPPED

Isolation & IPC

User processes run in separate address spaces. Service calls cross an IPC boundary with capability checks rather than relying on ambient authority.

Intent: make privilege transitions explicit and inspectable.
BOUNDED

Storage & files

AuroraFS is the native filesystem path, with ext2, FAT32, and GPT support in the documented platform scope. Durability and broad device coverage remain narrower than general-purpose systems.

Honest gap: limited service restart and storage validation.
SHIPPED

Network stack

VirtIO networking with DHCP, IPv4, DNS, TCP, UDP, and HTTPS-oriented workflows. This is a virtual-device path, not a promise of arbitrary NIC support.

Known gaps: no IPv6 and no Unix sockets in the current scope.
SHIPPED

Native workflow

GCC, Bash, Make, and musl-oriented development are the intended toolchain story. The deterministic package system produces bounded artifacts and a static package index.

Package repository: browse the current APT tree.
BOUNDED

Linux-compatible ABI

A practical compatibility layer supports selected Linux-shaped workflows without claiming Linux breadth. PTYs, swap, ASLR, and complete process semantics are not part of today’s promise.

Read the details in Technical Architecture.
